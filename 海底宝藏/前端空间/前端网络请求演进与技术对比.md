# 前端网络请求演进与技术对比



## 古法前端原来是制表员？



在没有 JavaScript(特别是 AJAX 技术)大行其道的前端“上古时代”，**HTML 的 `<form>` 表单绝对是前端向后端提交数据的“唯一且绝对的霸主”。**



那时候的 Web 开发和现在你用 Axios 完全是两个世界，咱们来盘点一下那个年代是怎么干活的，顺便解开一个后端历史遗留问题。



### 一、 上古时代：Form 表单的独角戏



在纯 HTML 时代，网页非常“老实”。你要做一个用户登录或者发布文章的功能，只能老老实实写一个 `<form>` 标签：





```html

<!-- 以前的前端是这么写请求的 -->

<form action="/api/users/login" method="POST">

    账号：<input type="text" name="username">

    密码：<input type="password" name="password">

    <button type="submit">登录</button>

</form>

```



用户点下“登录”按钮的一瞬间，浏览器的底层机制就会接管一切，把 `username` 和 `password` 按照特定的格式打包，顺着网线砸向后端的 `/api/users/login`。



### 二、 纯 Form 表单时代的“两大痛点”



那时候虽然能用，但体验非常折磨人，主要有两个致命缺陷：



#### 1. 致命白屏：全局刷新



这是当年最让人抓狂的地方。原生的表单一旦提交，浏览器就会**直接销毁当前页面**，傻傻地等待后端响应。



后端处理完后，不能像现在这样只返回一句 `"登录成功"` 或者一段 JSON，它必须**把整个下一个页面的 HTML 代码全部重新渲染一遍**，再扔回给浏览器。



这就导致以前上网，随便点个按钮提交数据，屏幕就会“白”一下，页面要整个重新加载。



#### 2. 天生残疾：只认 GET 和 POST



在实际开发中，很多后端接口会统一使用 POST，其实这也是历史遗留问题：**原生的 HTML `<form>` 标签，它的 `method` 属性只支持 `GET` 和 `POST`！**



在那个年代，即使你想优雅地使用 RESTful 风格的 `PUT` 或 `DELETE`，浏览器原生也是不支持的。大家被逼无奈，遇到不是查询的动作，统统用 POST 来解决，久而久之就养成了不用 `PUT` 和 `DELETE` 的习惯。



### 三、 JS 的逆袭：AJAX 与 Axios 登场



后来，JavaScript 彻底进化了，搞出了一个叫 **AJAX(异步 JavaScript 和 XML)** 的革命性技术。也就是你现在用的 Axios 的底层逻辑。



有了它，前端终于翻身做主了：



1. **拦截默认行为：** 点击按钮时，JS 瞬间出手，拦住表单不让它自己提交，**彻底消灭了页面刷新的白屏**。

    

2. **悄悄发请求：** JS 在后台悄悄把输入框里的数据抠出来，组装成优雅的 JSON 格式(`{"username": "xxx"}`)。

    

3. **解锁全套动作：** JS 绕开了 HTML 的限制，可以直接向底层发号施令，`GET`、`POST`、`PUT`、`DELETE` 随便用，完美契合了 RESTful 风格！

    

4. **局部更新：** 后端处理完，只返回一个 JSON 数据给前端。JS 拿到结果，在不刷新整个页面的情况下，悄悄把页面上的某个文字改成“登录成功”。

    



**总结一下：**



没有 JS 的时候，前端就是个只能靠 `<form>` 填表的“填表员”，每次填完都要重新排队领新表格；有了 JS 和 Axios，前端变成了“特工”，可以在后台悄悄和服务器交换情报，而不需要惊动整个页面。





##  JavaScript(特别是 AJAX 技术) 和axios和fetch有什么关系呢？



要把它们的关系理清，你只需要记住一个核心概念：**AJAX 是一种“思想”，而 Fetch 和 Axios 是实现这种思想的“神兵利器”。**



为了让你一眼看懂，咱们把这段历史当成一次“物流行业的升级”来看。



### 前端请求的四个时代



上古时代：HTML 表单 (没有 JS)



1990s



**方式：** 纯靠 `<form>` 标签发请求。



**体验：** 像**走路送信**。每次送信，整个驿站(页面)都要推倒重建(全局白屏刷新)。完全没有异步的概念。



启蒙时代：原生 AJAX (XHR)



2005年左右



**方式：** 浏览器底层提供了一个叫 `XMLHttpRequest` (简称 XHR) 的对象。



**体验：** 像**骑马送信**。前端终于可以悄悄把数据送出去，不用刷新页面了！这就是 **AJAX 技术**的诞生。但 XHR 的代码写起来极其繁琐、反人类，稍不注意就会陷入“回调地狱”(Callback Hell)。



现代原生：Fetch



2015年至今



**方式：** 浏览器觉得 XHR 太难用了，于是官方重新打造了一个全新的、原生的发请求工具，就是 `Fetch`。



**体验：** 像**自带的自动挡汽车**。它是基于 ES6 的 `Promise` 打造的，代码非常优雅。**重点：Fetch 是浏览器自带的，不需要安装任何第三方库就能直接用。** 它就是现代版的原生 AJAX。



终极外挂：Axios



现代工程化开发



**方式：** 这是一个由民间大神用 JavaScript 封装的**第三方开源库**(需要用 npm 下载安装)。



**体验：** 像**雇了个带私人管家的劳斯莱斯**。在浏览器端，Axios 的底层其实就是把当年那个难用的 XHR(新版 Axios 也开始支持 Fetch)重新包装了一遍。它帮你把所有脏活累活全干了。



### Fetch 和 Axios 到底选谁？



既然原生环境已经自带了优雅的 `Fetch`，为什么现代前端工程开发中大家通常还是首选 `Axios`？二者的核心区别又在哪？



因为 Axios 这个“管家”提供了很多开箱即用的工程化高级能力，但在现代 Web 标准下，Fetch 也在快速进化：



|**功能对比维度**|**Fetch (现代原生 Web API)**|**Axios (成熟第三方库)**|
|---|---|---|
|**安装与依赖**|运行环境原生内置，零额外依赖与包体积|需要 `npm install axios` 引入外部依赖|
|**JSON 转换**|❌ 较原始。需手动调用 `await response.json()` 解析|✅ 极简。自动序列化与反序列化 JSON，直接从 `res.data` 取值|
|**拦截器机制**|❌ 无原生拦截器。需自行编写高阶函数包装|✅ 极强。原生内置请求/响应拦截器，统一处理鉴权 Token、通用 Loading 与全局报错|
|**请求超时设置**|✅ **现代标准一行搞定**：`signal: AbortSignal.timeout(5000)`<br>*(注：早期需手动封装 `AbortController`)*|✅ 简单直观。直接在配置对象传入 `timeout: 5000` 即可|
|**HTTP 状态码错误判断**|⚠️ **易踩坑**：即便接口返回 404 或 500，Promise 依旧判定为成功 (resolve)，必须手动判断 `res.ok`|✅ **符合直觉**：默认遇到非 2xx 状态码直接判定为失败 (reject)，自动走入 `catch` 或拦截器|
|**跨平台运行环境**|✅ 现代主流浏览器、Node.js 18+、Bun、Deno 及 Serverless 边缘运行时均已全量内置|✅ 同构支持。在浏览器走 XHR/Fetch，在 Node.js 服务端走原生的 `http/https` 模块|

### 辟谣与进阶：现代 Fetch 的超时与中断



很多技术文章至今仍在断言*“Fetch 无法直接设置超时，是其致命软肋”*——**这属于 2018 年前的历史过时认知**！



#### 1. 历史过渡期做法（手动 AbortController）

在早期的 Fetch 规范中，确实没有内置的超时参数，开发者必须手动实例化控制器并启动定时器：



```javascript

// 早期陈旧写法：手动绑定 AbortController

const controller = new AbortController();

const timeoutId = setTimeout(() => controller.abort(), 5000);



try {

  const response = await fetch('/api/user', { signal: controller.signal });

  const data = await response.json();

} catch (err) {

  if (err.name === 'AbortError') {

    console.error('请求超时或被手动取消');

  }

} finally {

  clearTimeout(timeoutId); // 必须手动清除定时器防止内存泄漏

}

```



#### 2. 现代 Web 标准做法（原生 `AbortSignal.timeout`）

现代标准（**Node.js 17.3+、Chrome 103+、Firefox 100+、Safari 16+**）已经全量标准化支持 `AbortSignal.timeout(ms)`，仅需一行代码：



```javascript

// 现代标准写法：一行代码实现超时中断

try {

  const response = await fetch('/api/user', {

    signal: AbortSignal.timeout(5000) // 超过 5000ms 自动触发超时中断

  });

  const data = await response.json();

} catch (err) {

  if (err.name === 'TimeoutError') {

    console.error('请求超时！');

  }

}

```

### 技术选型建议



1. **果断选择 Fetch 的场景**：

   - 追求极致轻量、零外部依赖的小型项目或纯静态展示页面；

   - 现代前端公共 SDK、通用工具函数封装（避免强制为调用方引入 Axios 依赖）；

   - 现代 Node.js 18+ 服务端脚本、CLI 命令行工具或 Cloudflare Workers 等边缘运行时（Edge Runtime）。



2. **果断选择 Axios 的场景**：

   - 中大型企业级单页应用（Vue / React / Angular）；

   - 需要复杂的统一鉴权（JWT 自动无感刷新、401 统一拦截跳登录页、全局接口防重复提交与并发取消）；

   - 需要精确监听文件上传/下载进度的工程业务。



### 总结关系



1. **没有 JS 的时代：** 只能靠 `<form>` 刷新页面传数据，没有 AJAX 这回事。

    

2. **AJAX：** 它是利用 JS 悄悄发请求的**概念总称**(Asynchronous JavaScript and XML)。

    

3. **Fetch：** 浏览器亲生的现代 AJAX 实现方式，代码简洁，但缺一些高级功能。

    

4. **Axios：** 基于 AJAX 技术封装的第三方终极武器，把易用性做到了极致，是目前企业级开发的首选。
