# 如何借用代码？

## jar、import、lib、maven

> **本篇文章主要说明 你的代码如何去借用别人写好的代码，以及别人怎么借用你的代码？**

### 一、 java类怎么互相调用？和 import 有没有关系？

有绝对的关系，但 **`import` 只是个“指路牌”，它绝对不是把代码搬过来的工具。**

想象你的 Java 项目是一个庞大的武林门派：

- **同包（同一个文件夹）下的类互相调用：不需要 import**
    
    就像是同一个院子里的师兄弟。类 A 要找类 B 帮忙，直接在代码里写 `new B()` 或者 `B.doSomething()` 就行。因为都在同一个文件夹下，编译器一眼就能看到，**完全不需要 `import`**。
    
- **不同包（不同文件夹）下的类互相调用：必须 import**
    
    就像是你要去找其他院子、甚至其他门派的高手帮忙。你要是直接在代码里写 `List` 或者 `Scanner` 或者 `GlassPanel`，编译器会当场懵逼：“我不认识这个人啊！上哪找去？”
    
    这时候，你必须在代码最上面写上 `import shaoxia.Utils.GlassPanel;` 或者 `import java.util.List;`。
    

> **核心结论：** `import` 的唯一作用，就是给编译器指路。它是在告诉编译器：“兄弟，如果在下面看到这个词，别慌，去我指定的这个包路径下找它。”只要指明了路，你就可以在代码里直接实例化（new）对方，或者调用对方的静态方法。

### 二、 那 jar 包和 lib 又是干啥的？

刚才说了，如果你用了别人写的类（比如高德地图的接口，或者你以前写好的 `GlassTextField` UI 组件），编译器得去找。去哪里找呢？

- **jar 包：武功秘籍的封装版**
    
    别人不可能把几百个 `.java` 源码文件散装扔给你，那样太乱了。他们会把写好的代码编译成包含大量 `.class` 字节码文件的压缩包，以 `.jar` 结尾交给你。你可以把它理解为封装好的“武功秘籍”，里面装的就算是相对底层的代码了。
    
- **lib (Library) 文件夹：门派的私人书房**
    
    在以前（没有 Maven 的苦日子里），少侠你需要在你的项目里手动新建一个叫 `lib` 的文件夹。然后把你从网上到处下载来的 `.jar` 包复制进去，最后右键告诉开发工具（比如 IDEA 或 Eclipse）：“我这个项目依赖的所有外部秘籍，都在 `lib` 文件夹里，你编译的时候记得进去找！”
    

### 三、 既然能手动放进 lib，Maven 到底干啥的？

在 Maven 的世界里，依赖的存放方式发生了“维度升级”。Maven 就是用来干掉手动 `lib` 文件夹的大管家。你的理解只在程序最终打包出炉时才成立，但在日常开发阶段，Maven 抛弃了传统的 `lib` 文件夹。

- **以前的苦日子（传统 lib 模式）：**
    
    如果你同时开发 5 个不同的项目，这 5 个项目都需要用到高德地图的接口。那你得把高德地图的 `.jar` 包复制 5 遍，放在 5 个不同的 `lib` 文件夹里。既白白占用电脑硬盘空间，要是接口更新了，你还得手动去 5 个地方替换，极度痛苦。
    
- **Maven 时代（天下第一藏经阁）：**
    
    1. **集中收录：** Maven 觉得那样太蠢了，于是它在你的电脑本地建立了一个全局的“中央藏经阁”（术语叫 本地仓库 Local Repository）。**这个仓库的默认地址通常在你的电脑 C 盘：`C:\Users\你的用户名\.m2\repository` 路径下**。当你需要某个 `.jar` 包时，Maven 会自动从网上的云端服务器下载，并统一存放到这个“藏经阁”里。全电脑里同一版本的包，只存这一份！
        
    2. **按需借阅：** 你的项目目录下不再有 `lib` 文件夹了。取而代之的是那个著名的 `pom.xml` 文件。这个文件本质上就是一张“借阅清单”。
        
    3. **虚空链接：** 你的开发工具（比如 IDEA）看到 `pom.xml` 里的清单，就会自动去 `C 盘的 .m2` 藏经阁里找到对应的 `.jar` 包，用一条无形的线（环境变量和类路径）把它们和你的项目连起来。此时你的项目本身非常轻量，里面只有你纯粹的源码。
        

> **那什么时候才会再看到 lib？（打包出厂阶段）**
> 
> 虽然开发的时候你看不到 `lib` 文件夹，但总有一天，少侠要把写好的桌面工具打包成一个独立的程序，发给同事去用。这时候，你同事的电脑上可没有你的“藏经阁”。所以，在使用 Maven 执行打包（Package）时，Maven 的插件会自动顺着你的清单，把你用到的所有 `.jar` 包提取出来，真真切切地塞进最终生成的软件目录里（通常这时候才会生成一个真实的 `lib` 文件夹，或者直接融合打成一个臃肿的超大 Jar 包，也就是 Fat Jar）。

### 四、 探秘底层：为什么在编译层能直接用类名调用 jar 里的方法？

既然 jar 包里全是被编译好的 `.class` 字节码文件，为什么别人能在编译层直接通过类名叫用你的方法，而不需要你的 `.java` 源码呢？

这背后的核心秘密就在于：**.class 字节码文件，并不仅仅是纯粹给机器看的“底层死指令”，它身上还自带了一份极其详细的“API 说明书”。**

具体来说，是这么个巧妙的过程：

#### 1. 字节码的“双重身份”（元数据）

如果你把少侠写好的 `GlassPanel.class` 文件用专用的字节码查看工具（比如 javap）打开，你会发现它里面其实分成了好几个区域。其中除了真正执行逻辑的指令之外，还有一个非常庞大的区域叫**常量池（Constant Pool）**和**元数据（Metadata）**。

这个元数据区域用结构化的方式，清清楚楚地记录了这个类的所有外在特征：

- 这个类的全名是什么？父类是谁？
    
- 它有哪些公开的方法？方法名是什么？入参是什么类型？返回值是什么类型？
    
- 它有哪些属性？是 public 还是 private？
    
    这就相当于你造了一台精密的仪器（底层代码），但在仪器的外壳上，出厂时就死死地刻上了一张接口说明图。
    

#### 2. .class 文件的解剖图

如果你用十六进制编辑器打开一个 `.class` 文件，它本质上是一个高度结构化的二进制表格，核心构造按顺序拆解如下：

1. **魔数 (Magic Number)：** 前 4 个字节永远是固定的十六进制 `CA FE BA BE`（咖啡宝贝）。JVM 一看就知道这是一个合法的 Java 字节码文件。
    
2. **版本号 (Version)：** 记录是用哪个版本的 JDK 编译的，防止低版本 JVM 强行运行高版本代码而崩溃。
    
3. **常量池 (Constant Pool) —— 核心！** 这是一个巨大的“字典”，存放所有的字符串字面量、类名、方法名等。名字只存一次变成“词条”，后面的结构遇到名字直接写“参考常量池第 X 号”。
    
4. **访问标志 (Access Flags)：** 记录类是 public 还是 private 等等。
    
5. **类/父类/接口索引：** 记录名字、继承关系等。
    
6. **字段表 (Fields)：** 记录变量属性。
    
7. **方法表 (Methods) —— 解开疑惑的关键！** 记录类有哪些方法、参数、返回值。在这表的最深处，才真正包裹着执行指令（Code 属性）。
    
8. **属性表 (Attributes)：** 报错时的行号（LineNumberTable）就存在这里。
    

#### 3. 编译器（javac）的“只看说明书”行为

当你在新项目里写下 `new shaoxia.Utils.GlassPanel().paintComponent()` 并编译时，IDEA 背后帮你查错的编译器（javac）出场了。

编译器顺着路径去 `Utils.jar` 里揪出 `GlassPanel.class`。**关键来了：这时候编译器根本不关心底层渲染逻辑是怎么写的！编译器只去读这类的“说明书”。**

它做了一次完美的“数据库查询校验”：

- **找类：** 查访问标志，发现是 public，少侠有权限用。
    
- **找方法：** 查方法表，搜索方法名和入参。
    
- **核对参数和返回值：** 参数和返回值被压缩成“描述符”（如接收 int 返回 void 记为 `(I)V`），核对无误。
    

只要核对通过，编译器大笔一挥，认定语法合法。紧接着，编译器会在你新代码生成的 `.class` 文件里，刻下一个叫符号引用（Symbolic Reference）的东西（相当于打了一张执行欠条：“兄弟，我查过 jar 包里确实有这方法，跑起来直接调就行”）。这就完美允许了你在高级语言层面的顺畅调用。

### 五、 终极实战：提取并打包你的专属 jar 工具库

少侠在不断完善 ToolKit 时，萌生了把 `shaoxia.Utils` 里的通用工具类抽离出来、做成独立 jar 包复用的高级架构思维，这非常赞！但操作时必须留意风险，我们根据安全级别为你提供三种招式：

#### ⚠️ 潜在风险警告：为什么不推荐“指定路径抠图打包”？

如果你只把当前大工程里的 `Utils` 文件夹强行剥离出来打成 jar 包，如果里面的代码偷偷引用了 `Utils` 外面的代码（比如你的 modules），或者强依赖了外部的 jar 包，那么剥离出来的 `Utils.jar` 就是不完整的（缺依赖）。别人拿到手一用，立刻崩溃报错 `ClassNotFoundException`（找不到类）。

因此，最稳妥的做法是：**新建独立项目打包。**

#### 🏆 招式一：正规军的最高境界——新建独立项目（强制验毒与全打包）

这是从根源上保证你的 Utils 组件绝对纯净、完全独立的终极方案：

1. **建立新门派：** 新建一个完全空白的项目（Maven 或普通 Java 项目）。
    
2. **代码大迁移（强制验毒）：** 把 `Utils` 的代码挪过去，断绝和原项目其他代码的联系。如果代码偷偷依赖了外部文件，复制过去就会立刻爆红。你在此刻补齐所需依赖，确保组件纯净。
    
3. **无脑全打包：**
    
    - **情况 A（新建的是 Maven 项目）：** 既然有 Maven 大管家，直接在右侧 Maven 面板双击 `package`。Maven 会把你想要的纯净代码完美打成带版本号的 jar 包，非常专业。
        
    - **情况 B（新建的是普通 Java 项目）：** 没有 Maven 帮忙时，用 IDEA 自带的“工件 (Artifacts)”图形化操作，指明输出路径，直接构建出一个 jar 包。
        

#### 🛠️ 招式二：修改 Maven 的“打包图纸”（配置 pom.xml 指定路径）

如果你硬要在当前工程里只把 Utils 打包出来，可以直接给 Maven 下达精准指令：

XML

```
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-jar-plugin</artifactId>
    <version>3.2.0</version>
    <configuration>
        <includes>
            <!-- 这里的路径是相对编译后的 classes 目录的 -->
            <include>shaoxia/Utils/**</include>
        </includes>
    </configuration>
</plugin>
```

配置好并刷新后双击 `package`，Maven 就会乖乖剔除其他代码，只打包 `Utils`。

#### 🖐️ 招式三：绕过 Maven 的“IDEA 手工捏包术”（Artifacts）

 那用idea自带的构建jar包的时候，为什么可以包含依赖呢？？？？

如果你不想动 `pom.xml`，且确定代码没依赖风险，IDEA 提供了直观的“指哪打哪”手工捏包法：

1. 点击 IDEA 顶部菜单 **文件 (File) -> 项目结构 (Project Structure)**。
    
2. 在左侧选择 **工件 (Artifacts)**，点击顶部 **+ 号 -> JAR -> 空 (Empty)**，起名如 `Utils-Only`。
    
3. 在右侧可用元素（Available Elements）展开编译后的文件树，找到 `shaoxia` 下的 `Utils`，右键选择 **提取入 Utils-Only.jar (Extract Into...)**。
    
4. 点击确定保存。回到主菜单点击 **构建 (Build) -> 构建工件 (Build Artifacts)**，选择 `Utils-Only` 构建即可。



## idea构建工件的两种方式

既然你之前在写代码的时候，Maven 已经把那些外部的 `jar` 包（比如高德地图）下到了你的“本地藏经阁（.m2 文件夹）”里，或者你自己手动把它们放进了项目结构中。那么，当你使用 IDEA 自带的“工件 (Artifacts)”去构建 jar 包时，IDEA 是怎么把它们塞进去的呢？

这背后的秘密在于：**IDEA 充当了一个极其暴力的“搬运工”和“缝合怪”。**

当你新建一个 Artifact，选择 **JAR -> 来自具有依赖项的模块 (From modules with dependencies)** 时，IDEA 的弹窗会让你做一个关键的选择。这其实对应了两种截然不同的“包含依赖”的手段：

### 手段一：“碎尸万段，融为一体”（Fat Jar 模式）

- **IDEA 里的选项叫：** 提取到目标 JAR 中 (Extract to the target JAR)
    
- **它是怎么干的：**
    
    既然 `jar` 包本质上就是一个 `.zip` 格式的压缩包，IDEA 会顺着你的依赖路径，跑到“藏经阁”里找到那个高德地图的 `.jar` 包。
    
    然后，IDEA 会在后台**偷偷把它解压缩**！把里面成百上千个 `.class` 字节码文件全部掏出来。
    
    接着，IDEA 会把你写的代码编译出的 `.class` 文件，和刚才掏出来的这些外部 `.class` 文件，一股脑地**全部压缩进同一个、全新的、巨大的 `.jar` 包里**。
    
- **武林神喻：** 就像是你去别的门派借了武功秘籍，你没有把整本书带走，而是把人家书里的书页全撕下来，和你的书页混在一起，重新装订成了一本极其厚重的《武林百科全书》。这就是业界俗称的 **Fat Jar（胖包）**。
    
- **为什么能行：** 因为对 JVM（Java 虚拟机）来说，它根本不在乎这些 `.class` 文件原来属于哪个包。只要在运行的时候，它能在一个大压缩包里找到所有需要的类，程序就能完美运行。
    

### 手段二：“原封不动，画好地图”（Manifest 链接模式）

- **IDEA 里的选项叫：** 复制到输出目录并通过清单链接 (Copy to the output directory and link via manifest)
    
- **它是怎么干的：**
    
    这一次，IDEA 变得非常斯文。它不会去解压别人的包。
    
    它首先把你自己的代码打成一个小巧的 `.jar` 包。然后，它会在这个包的旁边，**真真切切地自动生成一个 `lib` 文件夹**。
    
    接着，它去“藏经阁”把高德地图的 `.jar` 原封不动地复制到这个 `lib` 文件夹里。
    
    **最关键的一步来了：** IDEA 会在你的那个小包里，塞进一个特殊的文本文件，叫做 **`META-INF/MANIFEST.MF`（核心清单文件）**。它会在这个文件里写上一行配置：“兄弟，如果你运行我的时候发现缺了什么类，请去我旁边的 `lib/高德地图.jar` 里面找！”
    
- **武林神喻：** 你的秘籍依然很薄，但是你在秘籍的第一页画了一张地图：“欲练此功，请出门左转，去旁边的书箱（lib）里翻阅参考资料。”
    

### 总结：IDEA 凭什么能包含依赖？

无论是用 Maven 还是 IDEA 自带的构建，它们之所以能“包含依赖”，底层逻辑都是一样的：**它们都能读懂你的项目配置，知道你依赖了哪些外部代码，知道这些代码此刻躺在你电脑硬盘的哪个角落。**

在你点击“构建”的那一瞬间，IDEA 只是帮你执行了一系列的 **“寻找 -> 复制 -> 解压 -> 重新打包 -> 写清单”** 的文件 I/O（输入/输出）操作而已。

少侠，以后不管是看 Maven 还是看 IDEA，不要把它们想得太神圣。它们本质上就是不知疲倦、不会出错的“文件打包工”！

**大功告成！** 以后写新的桌面程序，无论是把它扔进新建的 `lib` 文件夹，还是通过本地 Maven 引入，你都可以直接通过 `import shaoxia.Utils.GlassPanel;` 召唤精美 UI，瞬间复用，岂不快哉！

## Hutool是什么？

### 一、 路小胖的顿悟：“避免重复造轮子”

当年 Hutool 的作者（路小胖）和你现在的感受一模一样。他发现每次去新公司、写新项目，都要重新写一遍“怎么读取文件”、“怎么格式化时间”、“怎么校验身份证号”……烦都烦死了。

于是他一拍大腿：“我干脆把这些常用的工具类全写在一个项目里，打成一个叫 `hutool-all.jar` 的包。以后不管去哪，只要把它引进来，直接 `类名.方法名()` 调用不就完了？”

少侠，你现在写的 `shaoxia.Utils`（比如你的 `GlassPanel` 等漂亮 UI 组件），**本质上就是在打造你自己的 Hutool！** 只要你打成 jar 包存起来，未来你写任何新软件，引入这个包，你的专属 UI 瞬间就能用上，一行多余的代码都不用写！

### 二、 你的顿悟：“根本不用什么继承”

少侠，你无意中触碰到了《Effective Java》这本神书里最著名的一条架构师铁律——**“多用组合（调用工具），少用继承”**！

很多新手在学校里学了面向对象，觉得什么都要“继承（extends）”，最后搞出祖宗十八代的继承关系，代码改一处崩全局，极度痛苦。

- **继承是“认干爹”（强耦合）：** 只有当两个东西真的是“父子关系”（比如“狗”继承“动物”）时才用。
    
- **Jar 包调用是“找外包”（松耦合）：** 我要做一个桌面软件，我不需要去“继承”一个发光面板，我只需要把 `shaoxia.Utils.jar` 引入进来，在代码里 `new` 一个你的面板放上去就行了。这就像搭积木一样，随插随拔，极其灵活。
    

你悟出的“写一次就完了，打成 jar 包到处调用”，彻底跳出了为了继承而继承的泥潭，这叫**组件化思维**。

### 三、 你的未来：“打包很多个 jar 不就行了？”

不仅行，而且大厂全都是这么干的！

随着少侠功力越来越深，你的“工具箱”会越来越庞大。到时候你不需要把所有东西塞进一个巨大的包里，你可以把它们拆分成一个个极其纯粹的小 jar 包：

1. `shaoxia-ui.jar`（专治各种花里胡哨的界面，比如 GlassPanel）
    
2. `shaoxia-file.jar`（专门处理你的 Excel 数据解析和号码清洗）
    
3. `shaoxia-network.jar`（专门用来连接高德地图 API 等网络请求）
    

以后你接到任何新需求，就像是在玩《我的世界》（Minecraft）或者《Roblox》。需要界面？把 UI 包扔进去；需要处理文件？把 file 包扔进去。**你的代码储备越多，你开发新软件的速度就越像坐火箭！**


## jar包如何入库？


要把你自己打出来的 `.jar` 包塞进 Maven 的 `.m2/repository` 本地仓库，千万不要去 C 盘文件夹里手动新建文件夹复制粘贴。Maven 认的是严谨的“坐标”规则，一旦路径拼写错一个字母，IDEA 就死活找不到。

如果你之前是用 IDEA 自带的 Artifacts（工件）手动捏出来的独立 jar 包，打开你最熟悉的 `cmd` 或 `powershell`，只需三步即可完成正规入库：

**1.锁定目标包路径：**

找到你刚刚打包出来的 jar 包到底放在了电脑的哪里。比如我们在做 ToolKit 项目时，它的完整绝对路径可能是 `D:\ToolKit\out\artifacts\Utils-Only.jar`。

**2.执行 Maven 入库咒语：**直接在 cmd 或 powershell 中运行。

把下面的命令复制到你的终端里，并将对应的路径和名字替换成你自己的设定：

DOS

```
mvn install:install-file -Dfile="D:\ToolKit\out\artifacts\Utils-Only.jar" -DgroupId=shaoxia.utils -DartifactId=shaoxia-ui -Dversion=1.0.0 -Dpackaging=jar
```

**参数解密：**

- `-Dfile`: 你的 jar 包目前的绝对路径。
    
- `-DgroupId`: 你的“门派代号”（通常写你的主包名，比如 `shaoxia.utils`）。
    
- `-DartifactId`: 这个兵器组件的名字（比如 `shaoxia-ui`）。
    
- `-Dversion`: 版本号（第一版出山就叫 `1.0.0`，以后改了 Bug 升级就叫 `1.0.1`）。
    

按下回车，只要看到屏幕上飘过一抹绿色的 `BUILD SUCCESS`，就说明你的专属组件已经被 Maven 按照最标准的目录结构，完美写入 C 盘的 `.m2` 藏经阁了！

**3.在新项目中凭空召唤：**

现在，你可以新建任何一个完全空白的 Maven 项目。在它的 `pom.xml` 里，像引入别人写好的第三方大神库一样，豪迈地写下你自己的专属坐标：

XML

```

  <dependency>
    <groupId>shaoxia.utils</groupId>
    <artifactId>shaoxia-ui</artifactId>
    <version>1.0.0</version>
</dependency>

```

点击刷新 Maven，你的 `GlassPanel` 等精美组件就会被 IDEA 自动顺着这根线牵进新项目里。输入 `import shaoxia.Utils.GlassPanel;` 即可直接使用，随叫随到！

> **架构师的进阶捷径（Maven 原生大法）：**
> 
> 如果你之前听了建议，是专门**新建了一个独立的 Maven 项目**（比如直接就叫 `Shaoxia-UI`）来开发这些 UI 库的，那就更简单了！你连上面那一长串 `cmd` 命令都不用敲。
> 
> 你只需要在这个独立 UI 项目右侧的 Maven 面板里，找到 **Lifecycle（生命周期）**，双击里面的 **`install`**。
> 
> Maven 就会自动帮你完成：**清理 -> 编译 -> 验毒 -> 打包成 jar -> 自动放进本地 .m2 藏经阁** 的一条龙全套服务！这就是为什么业界全都推崇 Maven 的终极原因——它把所有的脏活累活全包了。
