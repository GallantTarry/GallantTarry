# static 修饰的静态变量运行后在jvm哪里？

### 一、 静态变量到底放在哪里？

**斩钉截铁的答案：在现今主流的 Java 版本（JDK 7 及以上，包括使用元空间的 JDK 8+）中，静态变量全部存放在【堆（Heap）】中。**

很多人对此产生混乱，是因为看了过于老旧的资料。为了彻底消除你的疑虑，我们做一个严格的界定：

1. **JDK 6 及以前：** 静态变量放在方法区（当时的实现叫“永久代”）。
    
2. **JDK 7：** 核心大手术。JVM 团队把静态变量和字符串常量池从永久代里抠了出来，**移到了堆（Heap）中**。
    
3. **JDK 8 及以后：** 永久代被彻底删除，换成了使用本地内存的“元空间（Metaspace）”。**但是！静态变量并没有跟着去元空间，它们依然死死地留在了【堆（Heap）】里。**
    

**在堆里的具体什么位置？**

当 JVM 加载一个类时，会在堆里生成一个代表这个类的 `java.lang.Class` 对象。这个类的所有静态变量，就紧紧地**依附在这个 Class 对象的尾部**。

- 如果静态变量是基本数据类型（如 `static int a = 1;`），数值 `1` 直接存在堆里的 Class 对象上。
    
- 如果静态变量是引用类型（如 `static Object obj = new Object();`），引用指针存在 Class 对象上，而真正的那个 `Object` 实例同样存在堆里的其他位置。
    

### 二、 编译与运行时的对象放在哪里？

要回答这个问题，我们需要先纠正一个底层的认知差异：“编译期”和“运行期”是不一样的。

#### 1. 编译期：不会产生真正的“对象”

当你执行 `javac` 把 `.java` 文件编译成 `.class` 字节码时，JVM 根本还没有启动，内存也没有分配。因此，**编译期不存在我们通常意义上说的 Java 对象**。

编译期只会把代码变成指令，把代码里写的固定字符串（比如 `"hello"`）变成一种叫“常量池字面量”的符号，存在 `.class` 文件的磁盘里。

#### 2. 运行期：对象创建的三大归宿

当你执行 `java` 命令，程序跑起来（运行期），执行到 `new` 关键字或者类加载时，对象才真正诞生。它们的归宿主要分为三种：

- **常规归宿：【堆（Heap）】（占据 99% 的情况）**
    
    只要你在代码里写了 `new User()`，无论是在普通方法里，还是赋值给静态变量，这个诞生的**对象实体一定是被分配在堆区**的。这里是垃圾回收器（GC）的核心工作区域。
    
- **特殊归宿一：【堆中的字符串常量池】（针对字面量）**
    
    如果你写的是 `String s = "少侠";`（没有用 `new`），运行期时，JVM 会在堆（Heap）中专门划出的一块叫做“字符串常量池”的区域内，创建或复用这个 `"少侠"` 字符串对象。
    
- **特殊归宿二：【栈（Stack）】（JVM 的黑科技优化）**
    
    这是展现专业深度的地方。现代 JVM 有一个极强的 JIT 优化机制，叫**逃逸分析（Escape Analysis）**。
    
    如果在运行期，JVM 发现你 `new` 出来的一个对象，仅仅在这个方法内部使用，完全没有被返回给外部，也没有被其他线程引用（即“没有逃逸”），JVM 为了提高性能、减轻 GC 压力，会通过“标量替换”技术，**直接把这个对象的成员变量打散，分配在当前线程的【栈帧】里**。方法一结束，栈帧弹出，内存瞬间释放，连垃圾回收都不需要。
    

### 总结提炼

- **静态变量：** JDK 7 以后，永远在堆（Heap）中的 `Class` 对象尾部。
    
- **方法字节码/类结构：** JDK 8 以后，永远在**元空间（Metaspace）**。
    
- **常规对象创建：** 运行期，在**堆（Heap）**。
    
- **局部极短命对象（未逃逸）：** 运行期，被 JVM 优化打散在**栈（Stack）**。

## 字节码/类结构是完整的.class吗？

**“方法字节码/类结构”确实来源于你硬盘上的 `.class` 文件，但它们并不是把 `.class` 文件原封不动地复制进内存，而是 `.class` 文件被 JVM “解剖、解析并重新组织”后的一大部分核心内容。**

为了让你彻底弄懂，我们可以把硬盘上的 `.class` 文件比作一个“压缩包”**，而元空间（Metaspace）就是这个压缩包解压后的**“文件陈列室”。

下面我为你详细拆解，当一个 `.class` 文件进入元空间时，到底发生了什么。

### 一、 硬盘上的 `.class` 文件是什么？

当你执行 `javac` 命令时，编译器会把你写的 `.java` 源代码翻译成 `.class` 文件。这是一个**极其紧凑的二进制文件**。里面密密麻麻记录了关于这个类的所有信息，包括魔数（用来识别文件类型）、版本号、常量池、访问标志、字段表、方法表、属性表等等。

它是给机器读的，但此时它还只是硬盘上的一段死数据。

### 二、 解剖到元空间：类结构与方法字节码

当 JVM 运行起来，需要用到这个类时，类加载器（Class Loader）就会把这个 `.class` 文件读进内存，对其进行“解剖”，并把解剖出来的信息分类存放到元空间（Metaspace）中。JVM 在底层（C++ 层面）会创建一个叫做 `Klass` 的数据结构来存储这些信息。

你提到的这两个概念，正是解剖出来的最核心的两个部分：

#### 1. 类结构 (Class Structure / Metadata) —— 类的“骨架”

这部分提取的是 `.class` 文件中的描述性信息（元数据）。存放于元空间后，它包含了：

- **身份信息：** 这个类叫什么名字（比如 `com.example.User`）？它的父类是谁？它实现了哪些接口？
    
- **权限信息：** 这个类是 `public` 的还是 `final` 的？
    
- **字段描述（注意，只是描述）：** 这个类有哪些成员变量和静态变量？它们叫什么名字？是什么类型（`int` 还是 `String`）？
    
    - _拓展：元空间里只存“有这个静态变量”的声明，而静态变量的“实际数值或对象实体”是被放在堆（Heap）里的，这就呼应了我们之前的结论。_
        

#### 2. 方法字节码 (Method Bytecode) —— 类的“肌肉与逻辑”

在 `.class` 文件的“方法表”部分，包含着你写在每个方法里面的代码。这些代码已经被翻译成了 JVM 能看懂的指令。

当你把 `.class` 文件解析到元空间后，这部分就是**方法字节码**。

- **它长什么样？** 比如你写了一句 `int a = 1 + 2;`，在元空间的字节码里，它可能变成了 `iconst_1`、`iconst_2`、`iadd`、`istore_1` 这样一条条的底层指令。
    
- **无论是普通方法、静态方法、还是构造方法**，只要是你写的业务逻辑，被编译成的所有字节码指令，全都被抽离出来，死死地钉在元空间里，供所有线程在执行时读取和调用。
    

### 三、 `.class` 文件的“一小部分”去了哪里？

你问它是不是 `.class` 文件的一小部分？其实，元空间几乎吸收了 `.class` 文件 90% 以上的核心信息，但经过 JVM 的解析，有一部分内容“分流”了：

1. **静态变量的实体分流：** 就像我们之前说的，`.class` 文件里记录了静态变量的定义，但运行时的实体对象/值被分流到了**堆（Heap）**。
    
2. **常量池的解析与分流：** `.class` 文件里有一个静态的“常量池”（存放字面量和符号引用）。加载进内存后：
    
    - 绝大部分变成了元空间里的“运行时常量池”。
        
    - 但是，里面的**字符串字面量**（比如 `"我是静态变量"`），在 JDK 7 以后，其实体被分流到了**堆（Heap）的字符串常量池**中。
        
3. **生成对外的“镜像”：** JVM 觉得元空间（底层 C++ 实现）里的数据太底层了，Java 开发者无法直接操作。于是它会在堆（Heap）里再凭空捏造一个 `java.lang.Class` 对象，作为元空间那个底层骨架的“照妖镜”（镜像）。你在 Java 代码里用的反射机制（Reflection），拿到的就是堆里的这个 Class 对象，然后通过它去间接访问元空间里的类结构。
    

### 总结

硬盘上的 `.class` 文件是原材料。

元空间里的“类结构”和“方法字节码”，是把原材料深加工后，构建出的供 JVM 高效运转的底层数据结构。它们构成了这个类在内存中的“绝对蓝图”。
